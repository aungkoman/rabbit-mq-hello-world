Microservices တွေပြောင်းသုံးတဲ့အခါ ကြုံရမယ့် အခက်ခဲဆုံးနဲ့ အရေးအကြီးဆုံး မေးခွန်းတွေကို သင်စဉ်းစားမိသွားပါပြီ။ Asynchronous (အချိန်ကိုက်စောင့်စရာမလိုတဲ့) စနစ်တွေမှာ "ငါခိုင်းလိုက်တာ ပြီးပြီလား၊ အဆင်ပြေလား" ဆိုတာကို ပြန်သိဖို့ နည်းလမ်း (၃) ခုလောက် ရှိပါတယ်။ သင်ပြောသွားတဲ့ အချက်တွေက အဲ့ဒီနည်းလမ်းတွေပါပဲ။

**၁။ API to API တိုက်ရိုက်မေးခြင်း (Polling)**
Service 1 က Message ပို့ပြီးတာနဲ့ Data ကို DB မှာ 'Pending' လို့ မှတ်ထားမယ်။ ပြီးရင် Service 2 ကို "ဟေ့... ခုနက email ပို့ပြီးပြီလား" ဆိုပြီး စက္ကန့်အနည်းငယ်ခြားတစ်ခါ API လှမ်းခေါ် (Poll) လုပ်ပြီး မေးမယ်။ (ဒီနည်းက အရမ်းရှုပ်ပြီး Server ကို ပင်ပန်းစေလို့ သိပ်မသုံးကြပါဘူး)။

**၂။ Webhook နဲ့ ပြန်ပြောခြင်း (Callback)**
Service 1 က Message ပို့တည်းက "မင်းအလုပ်လုပ်လို့ ပြီးရင်၊ ဒါမှမဟုတ် Error တက်ရင် ငါ့ရဲ့ `http://service-1/api/webhook/email-status` ဆိုတဲ့ လင့်ခ်ကို လှမ်းခေါ်ပြီး ပြန်ပြောလှည့်" ဆိုပြီး လိပ်စာထည့်ပေးလိုက်တာပါ။ ကြီးမားကျယ်ပြန့်တဲ့ System တွေ (ဥပမာ - Stripe Payment, Twilio SMS) တွေမှာ ဒီနည်းကို အများဆုံး သုံးပါတယ်။

**၃။ RabbitMQ ကနေပဲ API Server လို ပြန်ပြောခြင်း (RabbitMQ RPC Pattern)**
RabbitMQ မှာ ဒီလိုအခြေအနေမျိုးအတွက် သီးသန့်လုပ်ပေးထားတဲ့ **RPC (Remote Procedure Call)** ဆိုတဲ့ ပုံစံရှိပါတယ်။ ယခု သင်လေ့လာချင်တဲ့ "How things work" အတွက် အကိုက်ညီဆုံးနဲ့ RabbitMQ ရဲ့ စွမ်းရည်ကို အပြည့်ဝဆုံးပြမယ့် နည်းလမ်းဖြစ်ပါတယ်။

---

### RabbitMQ RPC Pattern ဘယ်လိုအလုပ်လုပ်သလဲ?

ဒီနည်းလမ်းမှာ Service 1 ဟာ Publisher အပြင် **Consumer (ပြန်နားထောင်သူ)** အဖြစ်ပါ အလုပ်လုပ်ရပါတယ်။

1. **Callback Queue ဖန်တီးခြင်း:** Service 1 က Message မပို့ခင် သူ့ဆီကို ပြန်စာပို့ဖို့ "Temporary Queue" (ဥပမာ - `amq.gen-1234`) တစ်ခုကို အရင်ဖန်တီးပြီး နားထောင် (Listen) နေပါတယ်။
2. **Correlation ID သတ်မှတ်ခြင်း:** Email ပို့ခိုင်းတဲ့ Job တစ်ခုချင်းစီအတွက် သီးသန့် ID (ဥပမာ - `job-email-001`) သတ်မှတ်ပါတယ်။
3. **Properties များထည့်ပို့ခြင်း:** Message ပို့တဲ့အခါ သာမန် Data တွေအပြင် RabbitMQ ရဲ့ Special Properties နှစ်ခုကို ထည့်ပို့ရပါတယ်။
* `replyTo`: `amq.gen-1234` (ပြန်စာကို ဒီ Queue ထဲထည့်ပါ)
* `correlationId`: `job-email-001` (ဒီ Job အတွက်ပါ)


4. **Service 2 မှ အလုပ်လုပ်ခြင်း:** Service 2 (Email Service) က Message ကို ဖမ်းမိပြီး Email ပို့ပါတယ်။ ပြီးတာနဲ့ သူဖမ်းမိတုန်းက ပါလာတဲ့ `replyTo` Queue ဆီကို Status (Success/Fail) ပြန်ပို့ပေးပါတယ်။ ပြန်ပို့တဲ့အခါ မူလ `correlationId` ကိုပါ ပြန်ထည့်ပေးရပါတယ်။
5. **Service 1 မှ လက်ခံရယူခြင်း:** Service 1 က `replyTo` Queue မှာ ဝင်လာတဲ့ ပြန်စာကို ယူ၊ `correlationId` ကို တိုက်စစ်ပြီး ဘယ် Email Job ရဲ့ အခြေအနေဆိုတာကို အတိအကျ သိသွားပါတယ်။

ဒီနည်းစနစ်က Service 2 ဆီကို Request ပို့ပြီး Response ကို Asynchronous ပြန်စောင့်တဲ့ပုံစံ (Message Queue ကို သုံးပြီး HTTP Request-Response လိုမျိုး တည်ဆောက်ထားတာ) ဖြစ်ပါတယ်။
